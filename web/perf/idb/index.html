Encodings

  • binary — store Uint8Array as-is (encode is a no-op).
  • base64 — padded (production btob64 shape).
  • base64u — unpadded base64.
  • base128 — 7-bit code units (repo btob128).
  • hex — 2 chars/byte.
  • latin1 — one JS string code unit per byte via String.fromCharCode (0–255). Same character count as raw length, but still a string (UTF-16 in the JS heap; IDB string storage ≠ raw binary key bytes). See notes below.

Workload (DIPLOMATIC-shaped)

  • encode/decode eid+pid — write/read tax like entityToStored / storedToEntity.
  • insert/apply — one tx bulk put (EntDB apply).
  • point — get(eid) + decode (single-entity load).
  • list-by-pid — compound index ["typ","pid"] getAll (children under a parent).
  • type scan — ["typ","crd"] range for one type.
  • getAll — full table (export/wipe; less common online).
  • ~80% of rows have a pid among ~500 parents; 5 types; small JSON body.

latin1 vs binary size

latin1 packs one byte → one string code unit, so the “key size” column shows the same number (e.g. 14) as binary’s byte length. That is not the same storage cost: binary keys are a byte sequence; string keys are DOMStrings. In V8, string data is typically 2 bytes per code unit in memory. On disk, Chromium IDB often stores strings in a form closer to UTF-16/UTF-8 metadata — high bytes (128–255) expand under UTF-8. Prefer binary for true 1:1 byte keys; latin1 is only interesting as a dense string encoding.
